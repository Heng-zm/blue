# MGS v0.2.0

Files, voice notes, encryption, and a faster wire protocol.

MGS 0.2.0 turns the mesh into a private file and voice channel. Set one shared
passphrase in Settings → Mesh and every message, file, and voice note is
encrypted with AES-256-GCM before it leaves the device. Relays still forward
traffic across the mesh, but they only see ciphertext. The JSON wire format is
gone as well: v2 uses fixed binary frames and envelopes, which is smaller and
much faster to parse on BLE links.

## New

- **File transfer** — send files from the chat composer. Files are encrypted as a whole, split into 4 KiB chunks, and reassembled with a SHA-256 integrity check.
- **Voice notes** — record up to **60 seconds** and send them as a normal message. AAC-LC on Android/iOS, WAV on Windows. Playback, pause, seek, and progress are built into the bubble.
- **Mesh encryption** — one shared passphrase derives a 256-bit key with PBKDF2-HMAC-SHA256 (120,000 iterations). Message bodies, attachment metadata, and attachment bytes are encrypted. Nearby broadcasts use the same passphrase, so they are private to the mesh instead of readable by every device in range.
- **Binary protocol v2** — binary `HELLO`, message envelopes, attachment descriptors, and blob chunks. Frames now use a 10-byte header with 16-bit chunk indexes, allowing large files over low-MTU connections.
- **Attachment progress and recovery** — transfer progress in the chat, a separate retry budget for unfinished files, automatic retry when a peer reconnects, and locked placeholders for encrypted messages received without the passphrase.
- **Passphrase settings** — set, change, or turn off the mesh passphrase. The chat header shows a lock when encryption is active and a warning banner when it is not.

## Changed

- `pubspec.yaml` version is `0.2.0+3`.
- Storage format is now version 2. Version 1 state files migrate automatically; old text messages remain readable, with no passphrase and no attachments.
- The attachment store lives in a `blobs/` directory next to `mgs_state.json`. Clearing history deletes stored attachments too.
- Android now declares `RECORD_AUDIO`; iOS adds `NSMicrophoneUsageDescription`.
- Relay, outbox, ACK, dedupe, and TTL behaviour are unchanged apart from operating on binary envelopes.

## Important: v2 is not compatible with v1

The frame header is wider, envelopes are binary, and v1 has no encryption or
attachments. **Update every device in the mesh to 0.2.0.** A v1 and v2 device
will connect, reject each other's `HELLO`, and disconnect. There is no
negotiation or mixed-version mode.

## Upgrade notes

- **Update all devices together.** v0.1.x cannot talk to v0.2.0.
- Existing text history is preserved. Encrypted messages arriving before the mesh passphrase is set are kept as locked placeholders; set the same passphrase and ask the sender to resend.
- Grant microphone permission on first record. If permission is denied, recording stops with a message instead of sending an empty note.
- Both devices must have MGS open at the same time. Windows does not need Bluetooth pairing — MGS connects through its own GATT service.
- iOS builds remain unsigned and require your Apple certificate and provisioning profile.
- The Android APK still uses the Flutter debug signing key.

## Known limitations

- No identity authentication or forward secrecy. Anyone with the passphrase can read and send; a malicious relay can spoof visible header fields.
- The passphrase is stored in plaintext in `mgs_state.json`. It is not encrypted at rest.
- Offline passphrase guessing is possible because the KDF salt is a fixed protocol constant. Use a long, random passphrase.
- ACKs are direct-link only; relayed delivery may still show `sent` or later `failed`.
- Failed file transfers restart from chunk 0. There is no partial-range resume.
- Interrupted incoming attachments are not resumed after an app restart; ask the sender to resend.
- No store-and-forward; undelivered messages retry for up to 5 minutes.
- Background BLE is best-effort. Keep MGS open for reliable meshing.
- iOS and Windows builds are unsigned. BLE requires physical devices; emulators and simulators cannot form a mesh.
